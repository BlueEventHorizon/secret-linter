# 機密情報の混入防止

リポジトリに含めてはならない情報と、その混入を検出するときの判断基準を定義する。
本文書は `/forge:secret-linter` が検査の根拠とする規範であり、重大度カタログの SoT でもある。

---

## 1. 前提 — 混入は「消せば済む」問題ではない

commit された秘密は、その後の削除・rewrite に関わらず**漏洩したものとして扱う**。git 履歴・fork・
CI ログ・ミラー・ローカルクローンのいずれかに残る可能性を排除できないためである。

したがって本文書の規範は「見つけたら消す」ではなく「**該当する秘密を失効・再発行する**」を伴う。
レビューの所見も、削除の指示ではなく失効の必要性の指摘として扱う。

この性質から、混入の検出は「見落としても後で直せる」種類の指摘ではない。パターンによる検出を AI による検出と併用し、
AI の読解だけに依存しない（§5）。

---

## 2. 含めてはならないもの

### 2.1 認証・認可の秘密

| 種別                 | 例                                                                |
| -------------------- | ----------------------------------------------------------------- |
| API トークン         | クラウド・SaaS・パッケージレジストリのアクセストークン            |
| 秘密鍵               | SSH / TLS / 署名鍵などの秘密鍵ブロック、キーストア                |
| パスワード           | DB・管理画面・サービスアカウントの実パスワード                    |
| 接続文字列           | 資格情報を埋め込んだ URI（`scheme://user:password@host/db` 形式） |
| セッション・署名済み | JWT・セッション Cookie・署名付き URL の実値                       |

### 2.2 秘密ではないが公開すると危険なもの

| 種別               | 例                                                       |
| ------------------ | -------------------------------------------------------- |
| 内部ネットワーク   | 内部ホスト名・プライベート IP・社内エンドポイント        |
| 個人情報           | 実在する個人のメールアドレス・電話番号・氏名             |
| 顧客固有の識別子   | 契約 ID・テナント ID・アカウント番号                     |
| 実在アプリの識別子 | 実在するアプリのパッケージ名（逆ドメイン形式の識別子）   |
| インフラ構成の詳細 | 実運用のバケット名・キュー名など、推測を容易にする識別子 |

§2.2 は §2.1 より判断が文脈に依存する。所属組織の公開方針が優先し、それが未整備の場合に本節を使う。

## 3. 許容される書き方

以下は混入ではない。所見として指摘しない。

- **環境変数・シークレットストアからの参照**（`os.environ["API_KEY"]`、`${{ secrets.TOKEN }}` 等）
- **明示的なプレースホルダ**（`<your-api-key>`、`xxxxxxxx`、`REPLACE_ME`、`sk-…` のような省略形）
- **公開が前提の値**（公開鍵、公開 API のエンドポイント、ドキュメント化された公式サンプル値）。例示・テスト入力に使うドメイン・IP アドレス・メールアドレスの公式サンプル値と、アプリのパッケージ名の例示（予約ドメインを逆にした `com.example.app` 等）は、§7.3 の文書用の予約値である。独自の架空の名前を作らず、予約値を使う
- **無効化済みであることが本文で明示された値**（失効済みの例示。ただし §4 の判断基準を満たすこと）
- **形式だけを示す構造説明**（`<32文字の16進文字列>` のような記述）

**判断に迷う場合は混入として扱う**（false positive を許容し、false negative を許容しない）。誤検出の
コストは 1 件の確認作業だが、見落としのコストは失効・再発行と影響調査である。両者は釣り合わない。

---

## 4. 実在の値を模した例示

ドキュメント・テストで「それらしい値」を書くとき、**実在の値をコピーして一部を改変したもの**は
使わない。改変が不十分な場合に実値が復元されうるうえ、レビュー時に実値との区別がつかない。

- 使う: 明らかに無効と分かる値（`AKIAIOSFODNN7EXAMPLE` のような公式に予約された例示値、`0` 埋め）
- 使わない: 実際に発行された値の桁を数文字だけ変えたもの

テストフィクスチャで検出パターンに一致する文字列が必要な場合は、行単位の抑制マーカーを使う（§5.2）。

## 5. 検出方式

### 5.1 構成

機密情報の検出と判定は、次の 3 つで構成する。検出する 2 つの手段（パターンと AI）は**併用する**。どちらか一方に寄せない。

| 要素               | 担うこと                                                                   | 得意                                                     | 不得意                                           |
| ------------------ | -------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| パターンによる検出 | 既知の形式と形式の手がかりに一致する値を、機械的に候補として挙げる         | 既知の形式（プレフィックス・鍵ブロック・高エントロピー） | 形式に当てはまらない秘密、文脈依存の §2.2        |
| AI による検出      | 形式を持たない混入（個人名・法人格の表記の無い会社名等）を候補として挙げる | 文脈判断、プレースホルダとの区別、§2.2 の妥当性          | 網羅性の保証。見落としても見落としたと分からない |
| 機密判定（§7、§8） | 候補を不合格・要確認・通過に分ける                                         | 同じ入力に同じ判定を返す（決定論）                       | 形式のない値の発見                               |

- AI による検出は、カスタム Agent `forge:secret-reader` が行う。この Agent は、検査対象の本文を読んで候補（位置・種別・値）を挙げるだけで、合否・区分は決めない。区分は機密判定が決める
- AI による検出は、`--rules-only` を付けない全ての指定で行う。`--rules-only` は、外へ出す直前の検査で速さを優先するための指定であり、AI による検出を省く
- AI が誤って挙げた候補は、機密判定で「要確認」になり、利用者の確認に落ちる。AI の見落としは、機密の名前リスト（§8）へ登録した後の検査から止まる
- パターンによる検出の結果を AI に渡し、真偽を AI に判定させることはしない。判定は機密判定が 1 か所で行う

### 5.2 抑制マーカー

検出パターンに一致するが混入ではない行には、行末に `secrets-scan: ignore` を含むコメントを置ける。

**抑制した件数と位置は、抑制されなかった検出と同じように利用者への結果表示へ必ず含める**。黙って除外してはならない。マーカーは「検査の目から隠す」機能ではなく「機械検出のノイズを分類する」機能である。マーカーの濫用そのものが所見の対象になる。

不合格の誤検出も、マーカーで通せる。検査の結果が不合格のときは、この通し方を、結果の末尾に示す。マーカーを付けるのは、利用者の了承を得てからである。

### 5.3 検出した値を示す相手 [MANDATORY]

検出した値は、示す相手を**利用者に限る**。

- 利用者への質問（要確認の確認）と結果の本文には、値を元のまま示す。マスクした情報では、利用者が機密かどうかを判断できない
- 呼び出し元へ返す区分、ログ、ファイルには、値を含めない。含められるのは、種別・位置・件数・理由までである
- AI による検出を行う Agent の最終応答にも、値を含めない（最終応答は呼び出し元の文脈に入る）

理由: 値が利用者以外の経路（呼び出し元の文脈・ログ・ファイル）へ出ると、混入を検出する行為そのものが新たな複製経路になる。

## 6. 重大度カタログ

| #  | 違反                                                               | severity    |
| -- | ------------------------------------------------------------------ | ----------- |
| 1  | 有効な認証情報の混入（§2.1 のいずれか）                            | 🔴 critical |
| 2  | 秘密鍵ブロックの混入                                               | 🔴 critical |
| 3  | 資格情報を含む接続文字列の混入                                     | 🔴 critical |
| 4  | 失効済みだが失効の明示がない認証情報                               | 🔴 critical |
| 5  | 実在の値を改変した例示（§4 違反）                                  | 🟡 major    |
| 6  | 内部ホスト名・プライベート IP・社内エンドポイントの記載            | 🟡 major    |
| 7  | 実在する個人を特定できる情報の記載                                 | 🟡 major    |
| 8  | 顧客固有の識別子・実運用リソース名・実在アプリのパッケージ名の記載 | 🟡 major    |
| 9  | 抑制マーカーの濫用（混入ではないことの根拠が確認できない）         | 🟡 major    |
| 10 | プレースホルダの形式が紛らわしく実値と区別しにくい                 | 🟢 minor    |

**#4 を critical とする理由**: 「これは失効済みだから安全」という主張は、レビュー時点では検証できない。
検証できない安全性の主張は、安全性の根拠にならない。本文で失効を明示し、かつ §4 に従った例示値へ
置き換えることを求める。

**#1 の修正内容**: 該当箇所の削除だけでは完了しない。§1 のとおり失効・再発行を伴う。所見への対応
報告には、失効の実施状況（実施済み / 実施予定 / 対象外と判断した根拠）を含める。

## 7. 機密判定

検出した候補（位置・種別・値）を、不合格・要確認・通過のいずれかに分ける。区分は候補の種別と値だけから決まり、同じ入力には常に同じ区分を返す。AI の出力は合否を決めず、候補として扱う。

- **不合格**: 外へ出してはならない。1 件でも不合格があれば、検査全体が不合格になる
- **要確認**: 利用者に値を示して確認する。確認後は、回答（§8）に従って扱う
- **通過**: 問題としない。結果の表示では、種別と値が同じものを 1 行にまとめる

要確認が残る間の全体の区分は要確認であり、全てが通過なら通過である。

### 7.1 判定の順序

候補ごとに、次の順で最初に当たったものを採る。

1. 機密の名前リストに一致する: 不合格
2. 種別が `package_name` で、予約ドメインを逆にした形（§7.3）、または許可リストのパッケージの接頭辞（§8.2）に一致する: 通過。不合格の種別が予約値と許可リストを通す、唯一の例外である
3. 種別が不合格の種別（§7.2）: 不合格
4. 文書用の予約値（§7.3）: 通過
5. メールアドレスで、許可リストに完全一致の項目がある: 通過
6. メールアドレス（上に当たらないもの）: 要確認
7. 許可リストに一致する: 通過
8. 種別が要確認の種別（§7.2）: 要確認

メールアドレスは、実在する個人の情報でありうるため、許可リストの完全一致の項目（そのアドレスだけを書いた項目）でしか通さない。ドメインの項目・`*.` の項目・同梱の公開ドメインでは通さず、個人のアドレスを一括で許さない。逆に、メールアドレスの項目は、ドメインの候補を通さない。

### 7.2 種別ごとの区分

| 区分   | 種別                | 内容                                           | 検出する手段 |
| ------ | ------------------- | ---------------------------------------------- | ------------ |
| 不合格 | `known_token`       | プレフィックスを持つ既知の形式のトークン       | パターン     |
| 不合格 | `private_key`       | 秘密鍵ブロック                                 | パターン     |
| 不合格 | `connection_string` | 資格情報を埋め込んだ接続文字列                 | パターン     |
| 不合格 | `jwt`               | JWT                                            | パターン     |
| 不合格 | `secret_assignment` | 秘密らしいキーへの値の代入                     | パターン     |
| 不合格 | `password_prose`    | 散文中のパスワード                             | パターン     |
| 不合格 | `package_name`      | アプリのパッケージ名（逆ドメイン形式の識別子） | パターン     |
| 要確認 | `high_entropy`      | 高エントロピーの文字列                         | パターン     |
| 要確認 | `company_hint`      | 法人格の表記を伴う会社名                       | パターン     |
| 要確認 | `obfuscated_host`   | 言い換えたドメイン・IP アドレス                | パターン     |
| 要確認 | `domain`            | ドメイン                                       | パターン     |
| 要確認 | `email`             | メールアドレス                                 | パターン     |
| 要確認 | `private_ip`        | プライベート IP アドレス                       | パターン     |
| 要確認 | `internal_host`     | 内部ホスト名                                   | パターン     |
| 要確認 | `person_name`       | 個人名                                         | AI           |
| 要確認 | `company_name`      | 法人格の表記の無い会社名                       | AI           |
| 要確認 | `resource_name`     | 実運用のリソース名                             | AI           |
| 要確認 | `other_ai`          | 上記に当たらない、AI が機密の疑いありとした値  | AI           |

種別はこの一覧が全てである。一覧に無い種別の候補は、通さずに検査の失敗として扱う。

`package_name` は、先頭のラベルが逆ドメインの根になる語（`com`・`org`・`net`・`io`・`jp`・`co`・`edu`・`gov`。大文字小文字は区別しない）で、3 つ以上のラベルを `.` でつないだ識別子である。`app`・`dev`・`me` のように、ファイル名や設定名の先頭にも現れる語は、根にしない。広く公開された開発系のパッケージ（`org.apache`・`com.apple` 等）は、§7.1 の 2 のとおり通過にする。

### 7.3 文書用の予約値

文書用の予約値は、インターネットの規格（RFC 2606・6761・5737・3849）が、説明や試験のために予約した、実在しない固定の値である。利用者が指定するものではない。予約値は通過にする（§7.1 の 4）。

- ドメイン: `example.com`・`example.net`・`example.org` とそのサブドメイン、末尾が `.example`・`.test`・`.invalid`・`.localhost` のもの、`localhost`。大文字小文字は区別しない
- IP アドレス: 説明用の範囲 `192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`（IPv4）と `2001:db8::/32`（IPv6）
- メールアドレスは、`@` の後ろのドメインで判定する
- アプリのパッケージ名: 予約ドメインを逆にした形、すなわち `com.example`・`net.example`・`org.example` で始まるもの（`com.example.app`・`org.example.demo.Main` 等）。大文字小文字は区別しない。`package_name` は不合格の種別だが、この形は通過にする（§7.1 の 2）

## 8. 2 つのリスト

機密判定は、利用者の確認を蓄積した 2 つのリストを使う。

| リスト           | 意味                                                        | 置き場                                                            |
| ---------------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| 機密の名前リスト | 外へ出してはならない値                                      | 利用者のホームの `~/.project-secret.yaml`（無ければ空として扱う） |
| 許可リスト       | 公開してよいと確認した値・ドメイン・URL・パッケージの接頭辞 | 同梱分と、プロジェクトの `.forge/secret_allowlist.yaml`           |

- 形式は、文字列だけのブロックリスト（`- 項目` を 1 行に 1 つ）である。コメント行（`#` で始まる行）と空行を許す。これ以外の書式は形式不正であり、検査を実行できなかったものとして扱う。形式不正の報告には、行番号と理由だけを示し、行の内容を示さない
- 両方のリストに一致した値は、機密の名前リストを優先する（§7.1 の 1）

### 8.1 利用者の回答とリストへの記録

要確認の候補は、利用者に確認する。回答は次のとおり扱う。

| 回答                     | 扱い                                                     |
| ------------------------ | -------------------------------------------------------- |
| 機密である               | 機密の名前リストへ追記する（ファイルが無ければ作成する） |
| 公開してよい（残す）     | 許可リストへ追記する                                     |
| 公開してよい（今回だけ） | 追記しない。その検査の間だけ通過として扱う               |

メールアドレスも、確認の選択肢は同じ 3 つである。「公開してよい（残す）」を選ぶと、そのアドレスを許可リストへ追記する（§7.1 のとおり、メールアドレスは完全一致の項目だけで通る）。

### 8.2 リストの一致方法

値は、URL・メールアドレス・ホストのいずれの形でも受け、スキームとユーザー情報とポートを除いたホストと、ホストより後ろ（パス・クエリ）に分けて扱う。

#### 機密の名前リスト

大文字小文字を区別しない（機密は広く一致させる）。項目の形で一致方法が変わる。

| 項目の形                                                          | 一致方法                                     |
| ----------------------------------------------------------------- | -------------------------------------------- |
| ドメイン名の形（ドットで区切った 2 ラベル以上の英数字とハイフン） | ホストの接尾辞（そのドメインとサブドメイン） |
| 英数字・空白・`_`・`-` だけの名前                                 | 語の境界（前後が英数字でない）               |
| それ以外（日本語の名前・メールアドレス・IP アドレス等）           | 部分文字列                                   |

#### 許可リスト

大文字小文字を区別する（許可は狭く一致させる）。プロジェクトの項目は、形で一致方法が変わる。

| 項目の形                   | 一致方法                             |
| -------------------------- | ------------------------------------ |
| `*.` で始まる              | そのドメインとサブドメイン           |
| `/` を含み、`?` を含まない | そのパスと配下（スキームは無視する） |
| 上記以外                   | 完全一致                             |

`接頭辞.*` の形の項目（`com.example.partner.*` 等）は、`package_name` の候補にだけ効く。パッケージの接頭辞として、ラベルの境界で前置き一致する（`com.example.partner.*` は `com.example.partner` とその配下のパッケージを通し、`com.example.partner` に文字を続けただけの別のパッケージは通さない）。他の種別の候補には、上の表の一致方法だけを使う。

メールアドレスの候補は、この表の一致方法ではなく、プロジェクトの項目との完全一致だけで通す。ドメインの項目や `*.` の項目は、そのドメインのメールアドレスを通さない。メールアドレスの項目は、完全一致でしか一致しないため、ドメインの候補を通さない。

同梱の許可リストは、次の 3 種類に分けて持つ。

- **パスまで公開のドメイン**: ホストの接尾辞で一致させる（`python.org` は `docs.python.org` も通す）
- **ホストだけ公開のドメイン**: コードのホスティング・デザインツール・文書共有・チャット等、URL のパス・クエリ・サブドメインに組織名・リポジトリ名・ファイル名など利用者ごとの内容が入るもの。そのドメイン自身と、`www.` 付きのホストだけの記載を通す。パス・クエリ・サブドメインを伴う URL は通さず、要確認にする
- **公開の開発系パッケージの接頭辞**: 広く公開された開発系のパッケージ名（`org.apache`・`com.apple`・`com.google`・`io.flutter` 等）の接頭辞。`package_name` の候補だけを、ラベルの境界での前置き一致で通す（`org.apache` は `org.apache` とその配下のパッケージを通し、`org.apache` に文字を続けただけの別のパッケージは通さない）。個人や組織が自分で持つ名前の領域（`io.github`・`com.github` 等）は含めない
